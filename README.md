# Среда исполнения LLM-агента

Прототип первого чекпоинта по Agentic LLM Systems, задание A.

Сервер создаёт отдельный CPU-сандбокс для каждой сессии. Клиент отправляет
команды по HTTP v0, получает события и финальный результат, отменяет выполнение
и закрывает сессию. Минимальный агентный цикл обращается к модели и выполняет
все инструменты через тот же API. Полноценное монтирование клиентской папки
пока испытывается отдельно от основного runtime.

## Первый чекпоинт

| Ориентир | Реализация и свидетельства |
|---|---|
| Сервер через Compose | Gateway и sandbox image собираются из исходников; healthcheck и loopback-порт |
| Харнес исполняет команды | Собственный минимальный цикл, реальный модельный smoke через API |
| Протоколы v0 | [Контракт и инварианты](track_a/protocol-v0.md), JSON Schema |
| Клиент подключается | [Терминальный клиент](track_a/README.md): сессии, exec, события, cancel, close |
| Первые ADR | [HTTP](track_a/docs/adr/0001-prototype-http.md), [сандбокс](track_a/docs/adr/0002-prototype-sandbox.md), [клиент](track_a/docs/adr/0003-checkpoint-client.md) |
| Раннер Б1–Б5 | [Результаты smoke и replay](BAF_RESULTS.md), фикстуры и программные чекеры |

Это результат стадии прототипа. Финальные требования курса шире ЧП1.
Нет интегрированного mount lifecycle, полноценного desktop UI, SSE, полного
базиса Б1–Б8 и сравнения нескольких пар «харнес + модель». Собственный харнес
прямо разрешён пунктом A-4.1; здесь используется минимальная собственная
реализация. Уникальность итоговой комбинации компонентов требует проверки.

Устройство агентного цикла: [docs/harness.md](docs/harness.md).
Краткий разбор к ЧП1: [docs/checkpoint-1.md](docs/checkpoint-1.md).

## Запуск

Нужны Linux, Docker Engine с Compose и Python 3.11+.
Из корня репозитория:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python checkpoint_checks.py A
.venv/bin/python checkpoint_checks.py A --infrastructure
```

Последняя команда запускает временные CPU-контейнеры и воспроизводит записанные
действия Б1–Б5. Модель и GPU ей не нужны. Первая сборка образов требует сети
для apt внутри контейнера; последующие проверки используют подготовленные
образы. Пакеты хоста не устанавливаются.

Для ручной демонстрации сервера и клиента см. [инструкцию](track_a/README.md).
Токен задаётся через окружение, образец -- `track_a/.env.example`.
Compose публикует случайный порт на 127.0.0.1.

## Эксперимент

Условия простого модельного smoke записаны в
[protocol-v1.json](track_a/baf/protocol-v1.json). На каждой задаче отдельная
сессия; чекеры и эталоны не передаются агенту. Исходный модельный прогон и
CPU replay хранятся раздельно. Replay проверяет программную цепочку, а не
увеличивает число независимых попыток модели.

`python3 baf_runner.py` обращается к уже работающему локальному HyperQwen.
Скрипт не запускает и не останавливает сервер. Ключ читается локально и не
сохраняется в результатах. Пригодность этой модели для итоговой оценки курса
ещё не подтверждена; текущий результат -- технический smoke.

## Ограничения архитектуры

У gateway есть доступ к Docker socket: это широкие права оператора, а не
доказанная граница безопасности. Команды агента выполняются в отдельном
непривилегированном контейнере без сети, с read-only root и ограниченными tmpfs.
SSHFS испытывался в отдельном диагностическом окружении с FUSE-правами.
Выявленные риски доступа, конфликтов и обрывов не объявляются решёнными.

Следующий этап -- интеграция монтирования с другой машины, клиентский интерфейс,
тесты изоляции и устойчивости, затем полный базис и сравнение пар.
