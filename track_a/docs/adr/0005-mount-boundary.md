# ADR 0005: план безопасной границы монтирования

Статус: proposed; не внедрено, не подтверждено тестами. Не даёт разрешения на
SYS_ADMIN/FUSE, изменение sshd, открытие портов или экспорт пользовательской папки.

## Требования

Клиент и сервер на разных машинах. `/work` должен быть настоящим mount, а не
копией с последующим sync. Нужны RO/RW, отсутствие остаточной серверной копии,
ограниченный экспорт и явный исход при потере связи. `.git`, ключи, служебные
данные харнеса не должны быть доступны через сетевую ФС. Тестовый root SSH key
из диагностики не подходит.

## Выбор для следующего прототипа

SSHFS в **доверенном mount broker**, SFTP exporter на клиенте и ограниченный
обратный туннель, а не FUSE/SYS_ADMIN в контейнере команды. Broker независимо
создаёт/отзывает mount и передаёт executor только проверенный lease ID, не
произвольный host path. Реальные привилегии и mount propagation сначала проверяются
на одноразовой ВМ; это отдельный этап с согласованием.

Обычный `chroot + internal-sftp` недостаточен: ограничивает верхний каталог,
но не прячет `.git` внутри него. Нужен экспортируемый namespace с явной политикой
защищённых путей. Кандидат — SFTP exporter, открывающий пути относительно directory
fd, запрещающий traversal, symlink и protected components во всех операциях,
включая rename/link. Проверка строкового prefix или resolve-before-open недостаточна
из-за гонки подмены пути. Реализация и доказательство этого свойства ещё впереди.

## Альтернативы

| Механизм | Достоинства | Цена/ограничения |
|---|---|---|
| SSHFS + ограниченный SFTP | Знакомый транспорт, обратный туннель, доступ к операциям файлов | FUSE broker, неоднозначные close/fsync при обрыве, exporter должен скрывать служебные пути |
| NFS поверх WireGuard | Стандартная сетевая ФС, подходящая семантика | Настройка ядра/сети, UID mapping и экспорта клиента, высокая цена для desktop и новичка |
| WebDAV/rclone mount | HTTP и более простой control plane | Кэширование/writeback осложняют подтверждение сохранения и конфликты; FUSE остаётся |
| Свой FUSE-протокол | Полный контроль lease/ошибок/версий | Самая большая реализация и поверхность ошибок; преждевременно для курса |

## План контракта (не текущий HTTP API)

Client exporter выдаёт capability только на выбранный каталог, режим и session ID,
с коротким сроком действия; ключ никогда не попадает в sandbox или model context.
Broker принимает provision lease, сообщает ready/read-only/read-write и состояние
соединения. Сессия становится open только после mount health probe. Внешний
пользователь не задаёт container image, host mount path или произвольный endpoint.

Потеря mount: ready → disconnected → closing. Новые инструменты запрещены;
активный run останавливается. Восстановление сети не переисполняет запись. Если
fsync/close не был подтверждён, результат `write_outcome_unknown`; нельзя обещать
сохранение или откат. Отключение: остановить процессы → unmount → revoke credentials
→ удалить временные mountpoints. При failed unmount сессия остаётся cleanup_failed.

Для первого прототипа: один агентный writer; клиенту явно показывается активная
запись. Это уведомление само по себе не предотвращает внешнюю правку. Нужны
предусловия по версии содержимого перед записью и тест lost update; обычное
монтирование не превращает редактирование в транзакцию. Честная гарантия до этого
теста — возможен конфликт, а не автоматическое слияние.

## Обязательные проверки перед интеграцией

Две машины/ВМ, RO и RW в обе стороны; traversal и symlink/rename races; защита `.git`
и canary-secret; отзыв capability; отключение при read/write/fsync/close; lost update;
закрытие при оборванной сети; отсутствие серверной копии; медиана/p95 операций ФС.
Текущий runtime эти требования **не закрывает** и отвергает mount-поля запроса.
