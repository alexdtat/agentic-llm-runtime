# Клиент ↔ сервер: задачи v1

Сессии создаются/закрываются маршрутами [v0](protocol-v0.md). Это временные
workdir без монтирования; неизвестные mount-параметры отклоняются.
Задача — одно сообщение и один запуск агентного цикла, не весь чат.
[Машиночитаемые объекты](protocol-v1.schema.json) проверяются интеграционными тестами.

| Метод | Путь | Вход → результат |
|---|---|---|
| POST | `/v1/sessions/{id}/tasks` | create_task → task |
| GET | `/v1/tasks/{id}` | task, events и result |
| POST | `/v1/tasks/{id}/cancel` | empty → task |

create_task: `{ "request_id": "client-key", "message": "задача" }`.
Сообщение — 1–8000 символов, транспортное тело до 16384 байт. Конфигурацию
модели, ключи, mount paths или docker flags нельзя передать этим запросом.
Повтор request_id в той же сессии с тем же payload возвращает тот же task;
другой payload — 409. Это действует после restart, пока сохранён volume.

Task имеет status running/complete/failed/cancelled. `result=null` до завершения;
terminal содержит status/error_kind/answer. `complete` означает finish харнеса,
а не доказанную правильность ответа. В mock mode это явно видно в model_backend.

Events: started, model (content/usage/seconds/backend), tool_started (run_id/argv),
tool_result (run_id/result), result. Sequence возрастает с 0; result только один.
GET возвращает сохранённую последовательность. Клиент восстанавливает отображение
по task ID и последнему sequence (`task-watch --after N`). Отключение клиента
не отменяет задачу; SSE и поток живого stdout пока не реализованы.

Одна задача занимает одну сессию: внешние exec получают 409. DELETE сессии
отменяет её активную задачу. Отмена отдельного run активной задачи отклоняется:
отменять следует task. После успешного task-cancel сессия закрыта и её tmpfs удалён.
Повторная отмена завершённой задачи возвращает исходный terminal.

Модельные ошибки/невалидное действие — model; неопределённый сбой HTTP executor —
transport; время — timeout; бюджет шагов — step_limit; история — context_limit;
перезапуск — interrupted; неподтверждённая очистка — cleanup_failed. Неуспешный
exit code команды сам по себе не завершает задачу: модель получает наблюдение.
Сбой инфраструктуры не повторяется автоматически. После рестарта нет
автоматического продолжения, поэтому потенциально выполненная правка не повторится.

Авторизация: общий Bearer token одного оператора, публикация только loopback;
многопользовательская изоляция и TLS не реализованы. Схема хранения событий
содержит пользовательские данные — удаление/срок хранения нужно учитывать отдельно.
