# SSHFS и Docker. Ограниченная диагностическая проба

Три сервиса на одном Linux-хосте. Exporter видит только синтетические
файлы. Broker монтирует `ubuntu@exporter:/work` по SSHFS. Sandbox без
сети получает именно этот mount в `/work`. Стенд диагностирует транспорт
и остановку контейнера. Для требования двух машин понадобится повторить
пробу с клиентом и сервером на разных Linux ВМ.

## Что требуется согласовать до запуска

- Два `sudo mount` только для нового каталога
  `/tmp/agentic-mount-probe.XXXXXXXX/mount` и последующий обычный
  `sudo umount` ровно этого self-bind. В случае остатка FUSE может
  понадобиться ещё один обычный unmount его дочернего `mount/work`.
  Флаги корня хоста не меняются.
- Broker получает `CAP_SYS_ADMIN`, `CAP_DAC_OVERRIDE`, устройство
  `/dev/fuse` (rw) и `apparmor:unconfined` для монтирования. Его
  rshared bind ограничен подготовленным `mount`, внутри него появляется
  `mount/work`. Docker socket в контейнеры не передаётся.
- Exporter получает `DAC_OVERRIDE, SYS_CHROOT, SETUID, SETGID` для sshd.
  Его writable bind ограничен `client`, а синтетический sibling-canary,
  конфиг и его часть ключей подключаются read-only. Broker читает свою
  часть ключей read-only. Sandbox получает только `mount/work` с
  rprivate и не имеет capabilities.
- Права на локальный Docker daemon для Compose. Нет `--privileged`,
  host network, опубликованных портов, GPU, скачиваний и LLM.
  Диагностический образ сверяется по ID, оба образа берутся из кэша.
- У каждого сервиса лимиты 0,5 CPU, 128 MiB RAM без дополнительного swap,
  32 PID и read-only root. В логах каждого контейнера до 1 MiB настройки
  ротации, tmpfs по 1 MiB там, где используется. Фиксированный тест пишет
  существенно меньше 1 MiB в синтетическую папку. Это объём пробы,
  файловой квоты в стенде нет.
- Сценарий с очисткой рассчитан примерно на три минуты по сумме дедлайнов
  отдельных команд. Exporter и broker имеют 180-секундный предел на
  процессы, sandbox — 120 секунд на каждый запуск. При таймауте mount
  может остаться, поэтому отдельный cleanup обязателен.

## Точные команды после согласования

В этом каталоге, из обычного пользователя с UID 1000. Скрипт обращается к локальному Docker через
`/var/run/docker.sock`. Daemon должен видеть тот же `/tmp`.

```sh
PROBE_ROOT="$(./probe.sh prepare)" && export PROBE_ROOT
test -d "$PROBE_ROOT/mount/work"
sudo mount --bind "$PROBE_ROOT/mount" "$PROBE_ROOT/mount"
sudo mount --make-rshared "$PROBE_ROOT/mount"
./probe.sh run > "$PROBE_ROOT/run.log" 2>&1
```

Даже после ошибки отдельно выполнить и проверить код возврата.

```sh
./probe.sh cleanup > "$PROBE_ROOT/cleanup.log" 2>&1 &&
sudo umount -- "$PROBE_ROOT/mount"
```

Cleanup удаляет sandbox первым, проверяет его отсутствие, пробует обычный
FUSE unmount из broker и удаляет контейнеры и сеть Compose-проекта.
При сообщении **Host FUSE mount remains** скрипт уже подтвердил отсутствие
контейнеров. Перепроверить точный child mount через
`findmnt -rnC --mountpoint "$PROBE_ROOT/mount/work" -o TARGET,FSTYPE`.
Если это ожидаемый fuse.sshfs, выполнить согласованный
`sudo umount -- "$PROBE_ROOT/mount/work"`, затем снова проверить отсутствие
child mount и снять self-bind. При занятом mount или неясном выводе
остановиться с логом. Каталог с логами, canary и одноразовыми ключами
остаётся под `/tmp` с правами 0700. Его удаление не входит в скрипт.
Ни скрипт, ни инструкции не используют lazy unmount или рекурсивное удаление.

## Читаем результат

1. Скрипт сверяет тип mount на хосте и содержимое файлов в обе стороны.
2. Он показывает доступ к `.git/probe`, результат чтения внешней ссылки и
   отдельную попытку доступа к sibling внутри chroot напрямую по SFTP.
   Обычный chroot охватывает `/probe`, а выбранный экспорт — `/probe/work`.
   `.git` и sibling ожидаемо выявят пробелы политики. Блокировка ссылки
   в sandbox не доказывает блокировку через SFTP, rename или hardlink.
3. Отдельный процесс делает `setsid`, переживает первоначальный exec и
   пишет heartbeat. Проверка сверяет host PID из Docker и отсутствие
   последующих изменений после stop. Это локальная проверка данного
   потомка, не исчерпывающая проверка изоляции.
4. После stop/start sandbox exporter отключается. Чтение существовавшего
   ранее файла пробуется впервые с дедлайном. Ошибка файлового транспорта
   и зависание имеют отдельный вывод. Timeout клиента сам по себе ничего
   не доказывает о прерывании kernel I/O.

Для переноса на ВМ поднять exporter с тем же синтетическим каталогом на
клиентской ВМ, а broker и sandbox с локальным probe self-bind на серверной.
Заменить Docker DNS `exporter` на адрес выделенного изолированного
канала между ВМ, обновить pinned known_hosts под это имя и ограничить
доступ к порту 2222 адресом broker. Повторить диагностику и очистку;
обратный SSH-туннель, RO/RW, защита путей и квота требуют своих проверок.

Для будущего адаптера Application нужны endpoint и provision с grant
вместо `/fixture` и `files`. По текущему коду `tool()` удерживает
session RLock во время HTTP к исполнителю. Отдельно проверить cancel во
время зависшего I/O и отделить отмену от этой блокировки, если подтвердится.
Application и харнес эта проба не меняет.
