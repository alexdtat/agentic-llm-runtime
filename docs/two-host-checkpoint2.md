# ЧП2 · Демонстрация A-2.3 и A-3.2 на двух машинах

**Статус.** На ThinkPad и desktop подтверждён обмен файлами в обе стороны через реальный SSHFS. В одной сессии ноутбук прочитал байты, записанные агентом, изменил локальный файл, и агент прочитал новые байты во втором run. Сессия закрыта. Desktop подтвердил снятие SSHFS и self-bind и удаление ресурсов брокера и sandbox. Внешние SSH-туннели и клиентский exporter имеют отдельный жизненный цикл.

## Что потребуется адаптировать

| Сторона | Действующие компоненты и изменения для демонстрации |
| --- | --- |
| Клиентская Linux-машина | CLI и отдельная синтетическая папка до 1 MiB. SFTP exporter запускается на клиенте с этой папкой в chroot под `/work` и с накладками на существующие `.git`. Временные пути здесь клиентские. Приватный host key exporter остаётся на клиенте. Его `authorized_keys` получает только открытый SFTP-ключ server-side broker. Порт exporter на клиентском хосте доступен только через IPv4 loopback. |
| Серверная Linux-машина | Application, mock, MountedExecutor и доверенный FUSE broker. Временные каталоги состояния и путь propagated `fuse.sshfs` в `SSHFS_MOUNT` создаются на сервере. Приватный SFTP-ключ создаётся на сервере и доступен только broker. MountedExecutor принимает один согласованный RW-грант и отдаёт sandbox bind в `/work`. Сеть sandbox отключена, ключи и Docker socket остаются вне sandbox. |

`prepare.py` сейчас создаёт общую временную структуру и обе пары ключей
одним вызовом. `stack.sh` управляет одним Compose-проектом. Закрытая
сеть `file-channel` и имя `exporter`, зашитое в SFTP preflight, SSHFS
и `known_hosts`, действуют внутри этого проекта. Для двух машин нужны
раздельная подготовка и очистка, настраиваемый адрес broker и сверка
открытого host key exporter из доверенного канала.

## Маршрут для согласования

Одна SSH-сессия от клиента к существующему SSH на сервере. Обратный
forward слушает **только server loopback** и ведёт к exporter через
client loopback. Прямой forward слушает **только client loopback** и
ведёт к Application на server loopback. CLI обращается к локальному
концу прямого forward. Для SSH-учётки согласовать только эти
forward endpoints, без внешних listeners. Клиентский ключ туннеля
остаётся у клиента. Переносятся только открытые ключи.

Для контейнерного broker кандидат — явный host-network **только для
доверенного broker** на выделенной серверной ВМ. Тогда preflight
и SSHFS обращаются к согласованному loopback-порту сервера, а
`known_hosts` закрепляет host key клиентского exporter за этим endpoint.
Текущий bridge-контейнер использует собственный loopback. Перед
демонстрацией отдельно подтвердить доступ именно из broker, отсутствие
внешнего прослушивания и появление `fuse.sshfs` в точной точке на сервере.
Маршрут требует изменений и проверки.

## Приёмка и завершение

### Запуск синтетической проверки

#### Повторяемый режим после одноразовой настройки

Один раз обновите публичный код на ноутбуке. Через уже аутентифицированный
SFTP можно передать три файла из `prototypes/mounted-runtime` в
`/work`: `two_host_laptop.py`, `two_host_pairing.py`,
`two_host_transport.py`. На ноутбуке перенесите их из `work` в каталог
уже установленного клиента, сохранив первый под именем `laptop.py`.
Переиспользуйте соседний `track_a/client.py` из исходного набора.
В экспорт передаётся только код.

Один раз настройте desktop и ноутбук из уже имеющихся копий одного и того
же файла credentials, подставив локальный путь на каждой машине.

```bash
# Desktop, из checkout
python3 -B prototypes/mounted-runtime/live_two_host.py --pair-from /path/to/credentials.json

# Ноутбук, в каталоге клиента
python3 -B laptop.py --pair-from /path/to/credentials.json
```

Desktop сохраняет broker key и pinned SFTP host key под
`~/.config/agentic-two-host/desktop`. Его gateway по-прежнему использует
`~/chp2-tunnel.3SY3Ma`. Ноутбук сохраняет ключ и authorized key exporter,
ключ туннеля и pinned gateway host key под `~/.config/agentic-two-host/laptop`.
При нестандартных исходных путях настройка принимает `--broker-keys` на
desktop и `--export-dir`, `--tunnel-key`, `--gateway-known-hosts` на ноутбуке.

Для следующих прогонов достаточно одной команды на каждой машине. Сначала
запустите desktop. Когда он сообщит о готовности gateway, запустите ноутбук
в течение пяти минут.

```bash
# Desktop
sudo -v && python3 -B prototypes/mounted-runtime/live_two_host.py --paired

# Ноутбук
python3 -B laptop.py --paired
```

Обе команды переиспользуют действующий transport или поднимают отсутствующие
gateway, exporter и SSH forwards с ранее закреплёнными ключами. Новый
exporter использует отдельный постоянный синтетический `work`. Команда
ноутбука поднимает недостающий forward, а desktop проверяет через обратный
forward закреплённый SFTP host key. После перезагрузки нужны прежний IP desktop
`192.168.0.8`, порты, pinned ключи и кешированные образы Docker. Transport
остаётся запущенным для следующего прогона. Сессия, runner, broker и
монтирования закрываются каждый раз. Теги и учётные данные Application
создаются заново для каждого прогона из приватного seed. Ноутбук проверяет
подпись свежего challenge по туннелю и получает публичный tag автоматически.

#### Одноразовый операторский запуск

На клиенте переиспользуйте согласованный exporter и SSH-туннель. Нужны прямой
forward с клиентского `127.0.0.1:24180` на серверный `127.0.0.1:24180`
и обратный forward с серверного `127.0.0.1:24222` на порт exporter
на клиентском loopback. На desktop из checkout запустите:

```bash
sudo -v && python3 -B prototypes/mounted-runtime/live_two_host.py
```

Перенесите на ноутбук напечатанный каталог с публичным кодом. Отдельно
перенесите файл credentials по доверенному каналу, например через USB.
Оставьте его вне экспортируемой папки и задайте ему права `0600`.
Подтвердите готовность в терминале desktop. После сообщения `Desktop ready`
на ноутбуке выполните, подставив фактические пути:

```bash
python3 -B laptop.py /tmp/chp2-client.EXAMPLE/work /path/to/private-credentials.json
```

Для остановившейся перед монтированием попытки `xgz0sec3` оставьте
подготовленные файлы на ноутбуке. Когда оба SSH forward готовы, на desktop
укажите исходный файл credentials с USB:

```bash
sudo -v && python3 -B prototypes/mounted-runtime/live_two_host.py \
  --resume-credentials '/media/USERNAME/USB/credentials.json'
```

Этот запуск переиспользует прежний tag и credentials, минует ожидание
Enter и выводит `Desktop ready` после готовности API. Затем выполните
ту же команду на ноутбуке с уже перенесёнными файлами. При обычном
запуске ожидание Enter не ограничено таймером. Перед монтированием при
необходимости снова откроется запрос пароля sudo.

Клиент откроет одну сессию, сверит агентную запись в локальном экспорте,
изменит отдельный файл с уникальным именем и попросит агента прочитать его
в той же сессии. Клиент выводит JSON с именем машины, ID сессии, ID запусков
и подтверждением закрытия. Desktop сохраняет итог, события и журналы
очистки в напечатанном каталоге. После проверки остановите клиентский
туннель и exporter и удалите перенесённый файл credentials.

1. Зафиксировать идентификаторы двух машин и сессию, открытую CLI на клиенте.
   На сервере подтвердить настоящий `fuse.sshfs` для RW-гранта.
2. Агент через mock и Docker записывает уникальный маркер в `/work/mock.txt`.
   На клиенте сверить байты в исходном каталоге. Затем вручную поменять
   `client.txt` на клиенте и получить новые байты отдельным агентным чтением
   в той же сессии. Сохранить ID запусков и события обоих инструментов.
   SFTP читает разрешённый canary и получает отказ для соседнего файла.
   Содержимое закрытых `.git` и ключи недоступны.
3. Закрыть сессию и подтвердить удаление sandbox и остановку писателей.
   Проверить снятие SSHFS и вспомогательного bind, остановку broker и
   exporter, удаление временных listeners и отзыв временных ключей.
   В свидетельства включить итог очистки без токенов и ключей. При
   неподтверждённой очистке сохранить диагностику и отметить прогон
   незавершённым.
   [Сценарий и cleanup](../prototypes/mounted-runtime/README.md)

## От оператора после обеда

- Назначения клиентской и серверной Linux-машин, окно доступа, адрес и
  порт существующего SSH сервера, имя тестовой учётки.
- Четыре согласованных loopback-порта для exporter и CLI на клиенте,
  обратного forward и Application на сервере. Разрешение на два forward
  и отдельный host-network для доверенного broker.
- Клиентский временный путь экспорта и серверный временный путь
  монтирования. Подтверждение доступности локального Docker на обеих
  машинах, готовых образов, FUSE и прав на точные mount/umount на сервере.
- Канал сверки открытых ключей SSH сервера и SFTP exporter.
