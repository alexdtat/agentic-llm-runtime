## Единый прогон проверок

После согласования оператор запускает из корня репозитория одну команду на Linux-хосте. Она использует существующие локальные образы, создаёт свежий синтетический RW-экспорт и снимает только ресурсы нового стенда. Нужны доступ к локальному Docker, cgroup v2, `/dev/fuse`, UID 1000 и права sudo на подготовку и очистку монтирований. Два доступных логических CPU нужны для проверки throttling.

```sh
sudo -v && PYTHONDONTWRITEBYTECODE=1 python3 prototypes/mounted-runtime/live_checkpoint2.py
```

Каталог журнала печатается строкой `Evidence directory`. В нём `checkpoint2.jsonl` содержит команды хоста и ответы worker, `checkpoint2-scenarios.json` хранит отдельные исходы и результаты очистки сессий, `checkpoint2-summary.json` — общую очистку контейнеров, процессов, сети и монтирований. Каталог сохраняется для проверки. Код возврата 0 означает, что прошли все сценарии, очистка каждой сессии и общая очистка. Отказ preflight выводится в терминал до создания рабочего каталога. Офлайн-проверки используют подмену Docker и приватного транспорта. [Офлайн-журнал](../results/t08-mounted-checkpoint2/offline-unittest.log) · [Mock-тесты](../tests/test_mounted_checkpoint2.py)

На одном хосте прошли все шесть сценариев. Закрытие каждой сессии подтверждено. Общая очистка завершилась с кодом 0, списки контейнеров, сетей, монтирований и процессов стенда пусты. [Результаты прогона](../results/t08-mounted-checkpoint2/live-mpc980c7/checkpoint2-summary.json) Функции проверки находятся в [live_checkpoint2.py](../prototypes/mounted-runtime/live_checkpoint2.py), команды sandbox — в [checkpoint2_commands.py](../prototypes/mounted-runtime/checkpoint2_commands.py). Для каждой проверки создаётся своя сессия с отдельным run. После run проверяются результат stop и отсутствие контейнеров этого runtime scope. При закрытии сессии проверяется освобождение гранта и записывается отдельный результат очистки.

| Сценарий | Функция | Критерий успеха | Исход | Очистка на хосте |
|---|---|---|---|---|
| Таймаут команды · A-5.1, A-5.3 | `CheckpointProbe.check_timeout` | Команда синхронно пишет единственный маркер и превышает дедлайн worker. Worker сообщает `timed_out/timeout`, Application возвращает `interrupted/outcome_unknown`. PID команды исчезает, диспетчеризация одна, lookup и попытки повтора получают 409, содержимое маркера совпадает с одной записью. | Прошёл | Подтверждена |
| Сеть и mock Model Proxy · A-5.4, A-5.5 | `CheckpointProbe.check_network` | Mock получает запрос Application и её наблюдение инструмента. Mock отвечает на health до и после проверки на том же адресе `127.0.0.1:<port>`. Sandbox получает `ECONNREFUSED` при единственном интерфейсе `lo` в отдельном сетевом namespace. | Прошёл | Подтверждена |
| CPU · A-5.1 | `CheckpointProbe.check_cpu` | После проверки cgroup два вычислительных процесса работают около двух секунд. Растут `cpu.stat: nr_throttled` и `throttled_usec`. | Прошёл | Подтверждена |
| PID · A-5.1 | `CheckpointProbe.check_pids` | После проверки cgroup `pids.current` доходит до 64. Следующий `fork` получает `EAGAIN`, `pids.events:max` растёт. Дети отпускаются через pipe и собираются родителем. | Прошёл | Подтверждена |
| Память · A-5.1 | `CheckpointProbe.check_memory` | После проверки RAM и swap отдельный дочерний процесс выделяет и трогает страницы. Родитель фиксирует `SIGKILL` дочернего процесса и рост `memory.events:max/oom/oom_kill`. | Прошёл | Подтверждена |
| Зависший SSHFS · A-5.3 | `CheckpointProbe.check_sshfs_hang` | После барьера команда читает холодный путь на SSHFS при поставленном на паузу брокере. Хост дважды наблюдает ожидание FUSE у того же PID. Application подтверждает `cancelled/requested` и stop по запросу с четырёхсекундным пределом ожидания. Проверяется исчезновение контейнера и процесса и возобновление брокера. | Прошёл | Подтверждена |

Пауза применяется только к контейнеру брокера, идентифицированному по меткам нового Compose-проекта. Если Docker не может подтвердить паузу или хост не даёт прочитать и распознать FUSE-символ в `/proc/<pid>/wchan` через `sudo -n cat`, сценарий записывает конкретный блокер, возобновляет брокер и проверяет очистку. Остальные проверки идут до паузы. Немедленный `ENOTCONN` подтверждён отдельным живым прогоном. [Журнал обрыва SSHFS](../results/t08-mounted-failures/live-rhsykxdx/verification.md)

Для статуса *подтверждено на хосте* нужны `passed` и `cleanup.status=confirmed` у соответствующего сценария и подтверждённая общая очистка. Замеры накладных расходов A-5.6 остаются отдельной задачей.
